# WebDAV sync

WebDAV keeps Papr libraries in step across computers. Open **Settings → Sync → WebDAV**, enter a directory URL, username and password (or app password), and connect. Use the same directory on every device. The directory's parent must exist; Papr can create the final directory. The account needs read, create, update and delete permission.

Choose **Sync** on the home toolbar (iOS/compact layout) or at the bottom of the sidebar (macOS), or **Settings → Sync → WebDAV → Sync now**, for the first merge and any manual run. In settings, choose the automatic interval: **1, 3, 5 or 24 hours**, shorter minute intervals, or **Manual only**. The default is **1 hour**, saved separately on each device. Save the interval to apply it. Timers and iOS foreground/network recovery share this interval, independent of feed refresh; failed and cancelled runs also wait for the interval after finishing. Manual runs bypass the interval and reset it, but cannot queue behind another operation. Manual only disables all automatic triggers. Pending data conflicts pause automatic sync until reviewed. macOS must remain running; iOS background execution is limited, so keep the app in the foreground to finish. The CLI uses the same database and sync implementation:

```sh
papr sync connect --provider webdav --url https://example.com/dav/papr/ --user USER --password APP_PASSWORD
papr sync run
papr sync status
papr sync disconnect --yes
```

Connecting tests access with a temporary file, without immediately transferring library data. Disconnecting removes this device's WebDAV credentials; it leaves the remote library in place. Use one sync service at a time; disconnect FreshRSS/Miniflux before connecting WebDAV, or vice versa.

## Included data

- Nested folders and subscription metadata, including parent/child and feed folder assignment and per-feed reading/refresh preferences.
- Article content, extracted full text, enclosure URLs, nested tags and their article assignments, highlights and notes.
- Filter rules, read/unread, starred and read-later flags, and the reader's scroll position.
- Saved AI summary prompt, active AI provider/model and Codex reasoning effort.
- Deletions and retention tombstones, so an old device cannot simply restore removed articles or subscriptions.

Credentials, API keys, email newsletter sources and their articles, other local settings, custom AI endpoint URLs, ChatGPT/Codex authentication, AI/translation caches, search indexes, downloaded images and media are excluded. Article HTML is sanitized on import, and the local search index is updated. Reading position is a fraction of the reader's scroll range; the embedded original webpage and audio playback positions are not tracked.

## Storage and conflicts

Papr stores a versioned JSON library as `papr-library-v1.json` in the chosen directory. The current payload is a **version 7 manifest** that references immutable gzip-compressed JSONL chunks (`papr-chunk-v6-<sha256>.jsonl.gz`) in the same directory. Versions 1–6 are still readable and migrate automatically on the first successful sync. Update all devices before syncing. Older versions fail safely on newer snapshots. It merges records by feed URL and article GUID, resolving references to each device's own database IDs. Existing local articles are not replaced by another SQLite file. Read, star, read-later and scroll-position edits have independent revisions. One-sided changes propagate, including read-to-unread changes, removed stars and moving the reading position backwards. Independent fields merge automatically. Changes to the same record on both devices are compared against this device’s last observed server snapshot; conflicting state or hand-edited metadata pauses sync before import/upload. Both versions are stored locally and shown under **Settings → Sync → WebDAV**. Choose **Keep this device**, **Keep WebDAV** or **Keep newer revision**, then sync again. A choice receives a new revision, so an older snapshot cannot undo it. If the local item changes while a conflict is displayed, the stale choice is rejected; sync again to refresh it. Folder/tag/rule/highlight metadata uses record-level revisions. AI provider, active model and reasoning effort share one coherent revision; the summary prompt has its own revision, so independent prompt and model edits merge automatically. Conflicting AI settings appear in the same review list. Restoring defaults is also synced. API keys, ChatGPT sign-in and custom endpoint profiles stay on each device; sign in separately on each computer. Synced AI settings apply to future summary, article-chat and AI-translation requests; existing cached summaries remain unchanged. An open prompt editor preserves unsaved drafts when remote changes arrive, and an unsaved model/endpoint draft offers an explicit reload action. Concurrent moves that would create a hierarchy cycle are detected before applying remote data, with a **Move to top level** resolution. Derived article-fetch metadata reconciles automatically using revisions, rather than prompting for every feed refresh. Keep computers' clocks reasonably accurate for edits made offline.

Deletion records are retained for offline devices. Renames use the old natural key's deletion and a new record. Exact duplicate rules or highlights with identical anchors are coalesced. There is **no 128 MiB whole-library limit** in version 7. Articles and each state kind use separate SHA-256 key buckets. Changed buckets are split at approximately **4 MiB uncompressed**, gzip-compressed and addressed by the SHA-256 of their compressed bytes. An individual record is limited to 64 MiB uncompressed, and the small root manifest is limited to 16 MiB (200,000 chunks maximum); these are defensive per-object limits, not a total library size limit. Old JSON snapshots retain their 128 MiB download bound for migration.

Only new or changed chunks are transferred. A reading-progress or star edit does not re-upload article bodies. Unchanged chunks are reused across retries and syncs. Local revision fingerprints avoid parsing and compressing unchanged article content. Large-library import/export walks disk-backed SQLite rows and bounded chunks instead of loading the whole library into memory. Only changed article content is imported and re-indexed, with dependency replay when feeds/retention change.

All referenced chunks are length/hash checked and decompressed with a strict output bound. A complete validated snapshot is staged on disk before conflict detection and the atomic library merge. Each upload writes immutable chunks first and then switches the root using conditional PUT. Interruption or a failed root update leaves the previous remote snapshot usable. Downloaded verified chunks and completed immutable uploads can be reused on retry; the current chunk may be transferred again. Local caches are pruned after successful sync, while remote chunks are retained so concurrent or offline readers never lose objects they reference. Do not manually delete chunk files independently of the manifest.

Update **all macOS and iOS devices before the first version 7 sync**. Old clients refuse the new root instead of overwriting it. A 1.3 GB SQLite file does not imply an equally sized transfer: search indexes and caches are excluded, and content is compressed. The first sync still needs to send all included content and may take time. Keep iOS in the foreground during that transfer; this does not add an iOS background-transfer entitlement. Allow additional local disk space for the incoming snapshot and compressed cache. Subsequent reading-state changes transfer small state chunks.

The server must implement conditional PUT (`If-Match` / `If-None-Match`) and return a **strong ETag** for the library file. Papr retries a changing remote root up to three times after downloading and merging the newer version. Every WebDAV request asks for `Accept-Encoding: identity`, so negotiated HTTP compression does not substitute a representation ETag for the stored resource validator. Article chunks remain gzip compressed. A rejected publication is checked by re-reading the root: an unchanged root after HTTP 412 is reported as a server/proxy version-check rejection, not proof of another device uploading. HTTP 409 reports a directory/server conflict separately. A successful upload whose response was lost can be acknowledged from the re-read manifest. No failure path falls back to unconditional overwrite. [Apache documents compression-specific ETag suffixes](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html#deflatealteretag); the user's authenticated provider behavior has not been measured. If the server lacks a strong ETag, the sync fails without an unconditional overwrite. This follows [WebDAV's ETag requirements](https://www.rfc-editor.org/rfc/rfc4918#section-8.6).

Malformed or unsupported snapshots fail validation, and a failed database merge rolls back atomically. If a download merges successfully but its upload fails, those remote changes remain locally and the next sync retries the transfer. The baseline tracks successfully observed downloads as well as completed uploads, so retries distinguish imported state from local edits. Settings show the last successful sync, pending conflicts and a failure indicator; choose **Sync now** to retry and see the error.

Remote chunks contain recoverable article content and notes: gzip compression is not encryption. WebDAV credentials are stored only in the local settings database, as with Papr's other connection settings. Use a private WebDAV directory and HTTPS for remote servers.

## Creating tag paths

Use `/` for hierarchy and `;` or `；` between multiple tags. For example, `agent/code;reading/to-sort` creates two paths and, in the article picker, attaches only `code` and `to-sort`. Existing ancestors are reused. Choosing a parent makes paths relative to that tag. The whole creation batch rolls back on an invalid path or conflicting name. Shared prefixes under the same parent are reused. Identical names under different parents are independent tags, and a parent’s article count is the distinct union of its own and all descendants’ article assignments. Hierarchy and leaf article assignments are included in WebDAV sync.

## Upgrading old folder labels

On the first startup after upgrading, folders named like `01 AI AGENT/公众号` become actual nested folders, including slash paths inside existing parents. Existing matching prefixes and exact destination paths are reused. **Only sibling names must be unique**: `AI/公众号` and `News/公众号` are independent folders. WebDAV version 7 uses full folder paths and upgrades v1–6 metadata without retransferring unchanged article chunks. Renames and moves update descendant keys and subscription references; deletions retain tombstones. Existing conflict versions and baselines are migrated too. OPML export/import keeps complete paths rather than grouping by basename.

The v2 conversion retries folders skipped by the previous release even if its v1 completion flag is set. Original leaf IDs, subscriptions and reading states are preserved where possible. Empty path segments and excessive depth leave the original folder intact; each path has its own savepoint. The conversion runs once per device and participates in normal sync conflict detection.

## Per-subscription cleanup

Settings → Subscriptions offers a previewed one-time cleanup and an automatic latest-100 policy per feed. The newest 100 use publication time (fetch time if absent), with GUID as a stable tie breaker across devices. Older starred, read-later or highlighted/noted articles are protected, so the retained total can exceed 100. Confirmations reject stale candidate lists rather than deleting newly protected content. Automatic cleanup runs after feed refresh. The policy and deletion markers sync through WebDAV, and old full-archive feeds cannot re-ingest purged GUIDs. Disabling the policy stops future cleanup; it does not restore deleted articles.

Offline annotations/collections on another device are preserved against cleanup: the protected article and associated state are restored with a newer revision and the purge marker is canceled. Conflicting user edits still require normal conflict review. Deleted article bodies are removed from local outgoing records. SQLite reuses freed pages; use Advanced → Compact database to reduce the file size. Previously uploaded immutable chunks remain remotely for concurrent/offline readers, so cleanup does not immediately reclaim WebDAV storage.

## Proxy routes, parallel transfer and progress

The transport now uses **five concurrent chunk requests by default**, adjustable from 1–8 in Settings → Sync → WebDAV → Transfer and proxy settings. Both request count and estimated compressed/decoded resident payloads are bounded (a 96 MiB admission budget); an unusually large individual record occupies the budget alone. This is a scheduling bound, not a claim about total process memory: SQLite, WebViews, indexing and runtime allocations add overhead. Article chunk format and conflict protocol remain v7, compatible with the enhanced.3 release.

WebDAV has its own proxy and request-timeout preferences. The default inherits the app network setting. Choose system proxy, direct, or an explicit `http://`, `https://`, `socks5://` or `socks5h://` proxy. On macOS/iOS, manual HTTP/HTTPS/SOCKS proxy settings are read from CFNetwork, including the system bypass list. SOCKS5h resolves the destination through the proxy. PAC discovery is not evaluated by this Rust transport; use an explicit proxy or direct with a VPN/TUN if PAC is enabled. Direct mode still uses the OS routing table, including VPN/TUN. The proxy software selects the Japanese exit node. An iPhone loopback address points to the phone, not a proxy on the Mac.

A fresh WebDAV client/pool is selected for each run, so a previous Japanese node's established connections do not stay attached after a route change. Within a run, connections are pooled and successful write-response bodies are drained for reuse. WebDAV requests default to 300 seconds total (configurable 60–1800), 15 seconds to connect and 60 seconds between reads. Up to three retries use backoff for transient network failures, HTTP 408/425/429 and selected 5xx errors; authentication, invalid data and ETag conflicts are not retried as ordinary transport failures. `Retry-After` is honored when at most 60 seconds; longer waits return an error so the user can retry later, without retrying before that interval.

Settings show the current stage, completed/total chunks, application payload bytes (manifests and compressed chunks), recent transfer rate and retry count. This is not a wire-level bandwidth meter, and compression/indexing stages are distinguished from network transfer. Stopping leaves completed verified objects available for the next run; cancellation takes effect at an async boundary. A root committed just before cancellation may already be visible remotely, and the next sync reconciles it normally.

Successful immutable uploads with a strong ETag leave a local receipt scoped to the endpoint and user. On retry, HEAD must match both the ETag and length before reusing that upload. Missing/changed metadata falls back to full content verification. Servers without a strong object ETag retain the verified GET fallback. The conditional root is still published only after all its referenced chunks are ready, and conflicts still pause before merging/uploading. Proxy URLs, timeout/concurrency options, upload receipts and transfer progress stay local.

The configurable concurrency and InfiniCLOUD setup flow were informed by [Remotely Save](https://github.com/remotely-save/remotely-save/blob/34db181af002f8d71ea0a87e7965abc57b294914/src/main.ts) and its [InfiniCLOUD guide](https://github.com/remotely-save/remotely-save/blob/34db181af002f8d71ea0a87e7965abc57b294914/docs/remote_services/webdav_infinicloud_teracloud/README.md). Papr retains its own SQLite record replication, content-addressed chunks and three-way conflict review; Remotely Save's file format is not used.

## A dedicated remote folder

For a new connection, enter the WebDAV address from InfiniCLOUD's **Apps Connection**, for example `https://domi.teracloud.jp/dav/`, and leave Remote folder as `Papr`. The resulting target is `https://domi.teracloud.jp/dav/Papr/`. A `/browser/` URL is the web interface, not the sync endpoint. Use the URL actually assigned to the account rather than assuming all accounts share a hostname/path. If entering a complete directory URL, leave Remote folder blank to avoid an extra nested `Papr` folder. Only one child collection is created; the configured parent must exist.

An existing connection offers **Copy into a new subfolder → Create and switch**. It copies only the library manifest and the chunks referenced by that snapshot, never unrelated root files. WebDAV COPY is preferred so the existing 1.3 GB library need not pass through the local proxy again. The destination uses `Overwrite: F`; the root COPY also checks the source ETag. Source changes trigger another snapshot attempt. An interrupted copy can resume using verified receipts. COPY-unsupported servers fall back to bounded upload/download for chunk manifests; legacy whole-JSON roots must first complete a normal sync to upgrade. A destination with a different existing library is rejected.

The connection URL changes only after a complete destination snapshot is ready. Pending local edits and conflict baselines are preserved and participate in the next normal sync. **The source files are retained**, so the move temporarily uses extra cloud storage. Pause syncing on other devices, switch every device to exactly the same new directory, then resume. Devices pointed at different folders are separate libraries; this does not publish an automatic redirect into the old root. After verifying the new folder on every device, old Papr files can be cleaned up separately. No source files are automatically deleted.
